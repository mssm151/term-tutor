## 一、作业总目标

选择「计算机教学智能体」中的**一个功能点**，按照部署思路完成方案设计，交付两件东西：

1. **项目设计方案**（文档）
2. **Git 项目仓库**（只需要框架，不要求完整实现）

业务场景覆盖计算机课程中的 Windows PowerShell 7、Linux 命令行、Docker 与 Kubernetes 实验教学，以及 SSH 远程操作教学；具体课程名称尚未确定。

### 已确认的功能方向与边界

- **服务对象**：学习命令行操作的学生。
- **产品形态**：类似 MobaXterm 的桌面终端与 SSH 客户端，以 Clide 的终端与 AI 协同交互为参考；中间为学生实际操作的终端，右侧为内置教学 Agent 对话侧边栏。学生无需另装 Claude Code、Codex 等外部 Agent CLI，自有 Agent 调用模型服务与本应用管理的终端探索工具。
- **Agent 侧栏行为**：关联当前选定的终端会话，自动获取已有终端上下文；可自主规划并执行探索，显示探索进展与结果，提供教学解释和候选操作命令。切换终端时明确显示会话归属，避免将不同主机的证据混合。
- **核心功能**：结合当前终端环境，提供命令讲解、操作指导、错误分析与候选命令。
- **模型上下文**：按用户最新要求采用 64k，即 65,536 token 总窗口；完整输入、生成输出及余量统一预算，具体见正式方案 d2。硬件容量及长输入等待时间留待实施验证。
- **目标环境**：Windows PowerShell 7、Linux、Docker、Kubernetes（K8s），支持 SSH 远程会话及 Windows COM/Linux 串口 TTY 的辅助。
- **串口边界**：串口为与本地 PTY、SSH 并列的连接适配器；按设备参数和实际控制台类型探查，不默认具备 Linux Shell、独立 exec、退出码或 SFTP。设备侧不安装 Agent，学生登录和实际操作不代做。
- **交互边界**：不替学生输入或执行教学任务中的操作命令；可以生成操作建议供学生自行执行。用户明确允许 Agent 为了解环境、调查问题和验证判断，自主执行探索命令，因此不是全面禁止 Agent 执行命令。
- **环境感知**：基础会话状态自动同步，Agent 可按问题主动调用工具、执行探索命令，逐步获取环境证据，避免要求学生反复手工描述或粘贴环境信息。
- **SSH 接入约束**：不要求在目标机器上安装或配置 AI Agent、常驻采集服务或模型运行环境；由本地客户端管理 SSH 连接，Agent 通过 SSH 执行探索并读取结果。
- **设计基线**：Electron 桌面端嵌入 Pi SDK，客户端维护 Agent 循环，Django 提供课程检索、记录与模型接入；Windows PowerShell 7 与 Linux Bash 为首批 Shell。具体运行版本及兼容性在后续实施时验证。
- **最新部署选择**：四台固定 x86 主机为 1 个控制平面（32 GB DDR3）、2 个 Worker（各 16 GB DDR3）、1 台数据机（32 GB）。数据机使用 2 TB SSD 与 4×2 TB HDD RAID10，约 4 TB 可用。独立推理区保留原 GPU 单机（64 GB RAM）并新增双机/四机 DGX Spark（每台 128 GB 统一内存，Arm CPU）配 DeepSeek-V4.1-Flash-1017，用户给定整套价格为 8 万/16 万元；三选一时整套为 5/6/8 台。按用户要求先给概略配置，不指定业务 CPU、主板或硬盘型号，完整总价和模型适配待确认。配置速览见[硬件配置概览](硬件配置概览.md)。

### 技术分工与实施边界

- **本次正式设计采用的 Agent 方案**：将 Pi SDK 嵌入桌面客户端，由 SDK 管理对话、模型调用与工具循环；不要求学生安装 Pi CLI。Django 负责课程 RAG、账号、学习记录和模型代理，不重复实现同一套探索循环。该设计不代表已完成工程验证。
- Pi 的工具需绑定本应用的终端/SSH/串口会话管理器，替换默认的本机执行与文件读写路径；Agent 运行时置于客户端后台进程，右侧页面通过受限 IPC 接收事件和发起对话。

- 主要采用本地终端/SSH 客户端管理会话、收集终端输出并提供探索工具的方式，不以远端预装采集组件为前提；Windows 支持 PowerShell 7，Linux 首版建议优先支持 Bash。需要更准确会话信息时，可研究临时会话内探测或 Shell 集成，不要求持久修改远端配置。
- 本地、SSH 远程、容器内会话分别绑定独立的环境上下文；进入与退出环境后须更新上下文，不沿用不匹配的旧状态。
- SSH 环境通过已建立的远程会话输出、主动探测与必要的 SFTP 文件读取获取；SSH 连接方式不决定远端操作系统与 Shell，需以实际证据为准。
- Docker 场景区分宿主机上学习 Docker 命令与容器内部学习 Linux 命令；不能用容器内部信息推断完整宿主机状态。
- 区分「当前 Shell 所在位置」与「工具实际操作的目标」：本地 PowerShell/Bash 中的 Docker 或 kubectl 命令也可能指向远程引擎或集群。
- Docker 上下文需考虑 context、相关白名单环境变量与命令显式参数；K8s 上下文需考虑 cluster、context、namespace、身份引用及命令显式参数，不将本地配置直接当作集群实时状态。
- K8s 场景区分通过 kubectl 学习集群操作与进入 Pod 内部的 Shell；容器/Pod 内部可通过受控 exec 探索或已接入的内部终端获取信息，无需预装 AI Agent，但受可用 Shell、工具及权限限制。助手的教学目标支持 K8s，与助手自身采用 K8s 部署是两项独立设计。
- 分离「学生交互终端」与「Agent 探索执行通道」：模型可生成探索命令，通过执行控制层在指定环境运行；教学操作建议只展示给学生，不自动写入其终端。
- 探索执行必须绑定目标主机、会话来源、工作目录及相关环境上下文；独立执行通道不会自动继承学生交互式 Shell 的全部状态，需通过 Shell 集成同步必要信息。
- 复用学生 PTY 能接触当前 Shell 状态，但必须协调输入与前台任务；单独 SSH exec 通道适合不占用学生终端的探查，但不能假定继承学生会话的目录、变量、别名或虚拟环境。具体方案应说明两类通道的选择和状态同步方式。
- 执行控制层校验目标与参数，并限制权限、时长、输出和资源占用；不将模型自称「探索」作为放行依据，也不依赖命令名称黑白名单判断任意 Shell 语句的实际影响。
- 默认优先使用观察与诊断操作；涉及安装、删改文件、变更容器/集群或重启服务等实际环境操作，应作为教学步骤交给学生。确需有副作用的验证实验时，建议在隔离测试环境中进行。
- 区分操作的教学目的与实际影响：即使命令只读，如果其本身就是要求学生练习的任务，也应避免直接替学生完成并展示整份答案。
- 首批环境字段可包含会话标识、采集时间、主机与容器标识、当前目录、Shell、用户身份、有限目录信息及白名单环境变量；不可观测的字段明确标记未知。
- 默认不要求挂载 Docker socket；若后续需要容器清单或挂载映射等宿主侧信息，应另行设计受限采集接口。
- Docker/K8s 实时状态可通过结构化接口或受控探索命令获取；权限不足或无法连接时明确标记未知，不自动上传 kubeconfig 原文、令牌、私钥或 Secret 内容。

## 二、交付物 1：项目设计方案

方案文档必须包含以下 5 个部分：

### a. 功能的介绍
- 选定的是哪一个功能点（只选一个，不要铺开）
- 解决什么问题、面向什么用户（学生 / 教师）
- 典型使用流程

### b. 大模型介入的方式是否合理
- 为什么这个功能需要大模型，而不是传统规则/算法
- 大模型以什么方式介入：提示词工程 / RAG / 微调，选哪种、为什么
- 合理性的论证与边界（哪些交给模型、哪些必须由程序或人工兜底）
- 需要**论证**，不能只罗列模型能力；原文未给出各项评分权重

### c. 数据来源、数据库设计、项目的可行性
- 数据来源：题库、教材/课件、历史答题记录等，分别从哪来、如何采集
- 数据库设计：给出具体的库表结构（表名、字段、关系）
- 可行性：技术上能否落地、数据是否拿得到、工作量是否可控

### d. 部署的方案、后期运维的说明
- 部署架构图与各组件职责
- 上线流程、环境要求
- 后期运维：监控、日志、备份、模型更新、故障处理

### e. 甲方部署的费用（硬件要求）
- 服务器 / GPU / 存储 / 带宽的具体规格
- 按规格估算的费用清单

## 五、历史硬件预算输入（完整部署预算以正式方案为准）

### 总体特征
- **服务器平台**：原材料按服务器 CPU 与多通道内存规划；具体型号、PCIe、供电及带宽是否足够需在实施时验证，不预先认定不存在瓶颈
- **加速卡**：Tesla T10 16G（Turing 架构，支持 FP16 / INT8）
- **模型**：各模型架构分别核对，低比特权重量化作为部署方向，不笼统认定全部为 MoE
- **多卡**：具体分配或并行方式与驱动、量化、引擎一起验证

### 三套配置

| 方案 | GPU | 总显存 | 内存 | 部署模型 | 定位 |
|---|---|---|---|---|---|
| 方案一 | 4 × Tesla T10 16G | 64 GB | DDR3 256G（4 通道，服务器平台） | Qwen3.8 Flash Next 125B A6B（沿用历史名称，实施时核对权重） | 大模型备选预算 |
| 方案二 | 4 × Tesla T10 16G | 64 GB | DDR3 64G（4 通道，服务器平台） | Qwen3.8-27B | 正式方案的主设计预算 |
| 方案三 | 2 × Tesla T10 16G | 32 GB | DDR4 32G（4 通道起，服务器平台） | Qwen3.6-35B-A3B | 较低单机预算的比较项 |

### 部署要点
- 低比特权重需结合实际量化格式和内核验证，不仅根据单卡显存决定可用性
- 权重格式和计算精度分开说明，正式方案以 AWQ W4A16 为验证方向，不把 INT4 权重等同于所有计算均为 INT4
- 模型推理服务与 Django 业务、向量数据库分离部署，模型服务独占 GPU 节点
- 正式方案将小型嵌入服务放在业务 CPU 节点；GPU 主要留给大模型，预留实际运行开销

## 六、已选功能点：环境感知型命令行教学助手

围绕 Windows PowerShell 7、Linux、Docker、Kubernetes（K8s）、SSH 和串口 TTY 实验中的命令行学习提供辅助。Agent 结合会话状态、按需工具调用、自主探索执行和教学资料检索，解释命令、分析问题并生成操作建议；教学任务中的操作由学生自行输入和执行。

大模型负责理解学习意图、规划探索步骤、选择工具、根据证据调整调查路径并生成教学解释；RAG 提供课程资料、命令手册与错误案例；环境组件提供会话事实并执行经控制层校验的探索请求。具体技术选型与部署方式仍需在设计方案中论证。
